# Brooklyn Bowl — мультигородской сайт

Статический сайт сети Brooklyn Bowl (боулинг, кухня, мероприятия) на несколько городов.
Один и тот же шаблон страниц (шапка/подвал/формы/стили) переиспользуется под каждый город,
контент каждого города лежит в своей папке.

Технологии: чистый HTML + кастомный лёгкий JS-фреймворк (`support.js`, `image-slot.js`),
без сборки, без npm. Правки — это прямое редактирование HTML-файлов.

## Куда публикуется

Один и тот же коммит пушится в **два** репозитория:

| Remote | Repo | Назначение |
|---|---|---|
| `origin` | [BrooklynBowl/tyumen-new](https://github.com/BrooklynBowl/tyumen-new) | рабочая/резервная копия |
| `pages`  | [BrooklynBowl/brooklynbowl.github.io](https://github.com/BrooklynBowl/brooklynbowl.github.io) | боевой сайт (GitHub Pages, ветка `main`, папка `/`) |

Живой адрес: **https://brooklynbowl.github.io/**
- `/` — страница выбора города (корневой `index.html`)
- `/tyumen/` — сайт Тюмени
- `/izhevsk/` — сайт Ижевска

После любых правок:
```bash
git add -A && git commit -m "..."
git push origin main
git push pages main
```
Пушить нужно в оба remote вручную — они не связаны между собой.

├── tyumen/                  ГОТОВ, живой город
│   ├── *.html                23 страницы

│   ├── support.js             общий JS-фреймворк рендера (байт-в-байт одинаковый во всех городах)

## Как добавить новый город — пошагово

Ориентируйся на то, как был добавлен Ижевск. Понадобится ZIP-архив экспорта с именем
вида `<Город> — Брулин боул сайт 2026.zip` (обычно в Загрузках).

1. **Распаковать архив через Python, не через `unzip`.**
   Стандартный `unzip` ломает кириллицу в именах файлов (это не только имена страниц —
   в `uploads/` половина файлов названа по-русски: блюда, PDF-меню и т.д.). Python же
   успешно правит кодировку сам:
   ```python
   import zipfile
   zipfile.ZipFile('Город — Брулин боул сайт 2026.zip').extractall('путь/для/распаковки')
   ```
   Внутри архива обычно один корневой каталог (`<город>-сайт/` или `<город>-site/`) —
   его содержимое и есть будущая папка города.

2. **Переименовать `*.dc.html` → `*.html`.**
   Экспорт отдаёт файлы страниц с суффиксом `.dc.html`. Если имена файлов уже латиницей
   без пробелов (как у Ижевска — `about.dc.html`, `afisha.dc.html`…) — просто срезать
   `.dc`. Если имена кириллицей/с пробелами (как было у Тюмени — `Brooklyn Bowl -
   Афиша.dc.html`) — придётся вручную придумать понятный латинский slug (в Тюмени так
   получились `events.html`, `bowling.html`, `kitchen.html`, `index.html` из
   «Афиша/Боулинг/Кухня/Главный»). **Файлы в `uploads/` НЕ переименовывать** — они
   остаются как есть, даже с кириллицей и пробелами в имени (так исторически сложилось
   и в Тюмени, трогать не надо, ссылки на них и так работают через `%20`).
   Главную страницу (`index.dc.html` / `Главный.dc.html`) — в `index.html`.

3. **Обновить все внутренние ссылки на новые имена.**
   После переименования грепни по всем `.html` файлам нового города на `.dc.html`,
   `%20` и кириллицу в `href=`/`src=` — не должно остаться ни одного (кроме ссылок на
   файлы в `uploads/`, там это нормально). Отдельно проверь city-picker в шапке и блок
   «В других городах» в подвале — там ссылки на соседние города вида
   `../tyumen/index.html`, `../izhevsk/index.html` и т.д. Экспорт нового города обычно
   копирует этот блок из шаблона предыдущего города буквально — там почти гарантированно
   будет битая ссылка на прошлый город (см. раздел про особенности экспорта ниже).

4. **Переместить сырое содержимое в папку города**, если ещё не так: все `*.html`,
   `uploads/`, `support.js`, `image-slot.js` — на верхний уровень `<город>/`. В корне
   репозитория ничего города-специфичного оставаться не должно (только общий
   `index.html`-выбор города и общие фавиконы).

5. **Скопировать юридические страницы.**
   В экспорте почти никогда нет `privacy.html`, `oferta.html`, `consent.html`,
   `info.html`, `legal.html` — их берём из уже готового города (Тюмень) как есть:
   - Взять файл `tyumen/<page>.html` целиком.
   - Заменить в нём блок **шапки** (`<header>...</header>` + идущий следом
     `<div data-m="mobile-menu">...</div>` + `<div data-m="tabbar">...</div>`) и блок
     **подвала** (`<footer>...</footer>`) на аналогичные блоки с любой уже рабочей
     страницы нового города (например `about.html`) — они у всех страниц одного города
     побайтово идентичны, можно смело брать с любой.
   - Текст самого документа (152-ФЗ, реквизиты и т.п.) **не трогать** — он одинаковый
     для всех городов, кроме одного момента:
   - В `legal.html` два юрлица: **Оператор** (ООО «Кегли кухня рок-н-ролл» — общий на
     всю сеть, реквизиты и адрес в Тюмени, не меняются) и **Обработчик** — это местное
     юрлицо конкретного города, его ИНН/ОГРН/адрес нужно получить от заказчика и
     подставить в реквизиты-карточку и во вводный текст.
   - В `privacy.html`/`oferta.html`/`consent.html` замени title и подзаголовок
     («Brooklyn Bowl Тюмень» → «Brooklyn Bowl <Город>»).
   - Если в тексте документа есть ссылка на `legal.html`, а вы ещё не создали эту
     страницу для нового города — временно поставь `href="#"`, и не забудь вернуть
     `legal.html`, когда страница появится (см. следующий пункт).

6. **Прописать в подвале все 22(+) страницы города**: `privacy.html`, `oferta.html`,
   `consent.html`, `info.html`, `legal.html` вместо `href="#"`, плюс ссылка «Все права
   защищены» на гугл-диск-документ (у всех городов один и тот же файл — уточни, если для
   нового города должен быть свой). Пункты, для которых страниц реально нет
   (Сертификаты, Блог, Аренда площадки, Доставка, Франшиза) — оставить `href="#"`, это
   ожидаемо и одинаково для всех городов на сегодня.

7. **Чекбокс согласия в формах.**
   В каждой форме бронирования (`corporate`, `dr`, `dr-kids`, `graduation`, `friends`,
   `family`, `lane`, `loyalty` — итого 8 форм на город) вместо статичного текста
   «Нажимая кнопку, вы соглашаетесь…» должен быть **активный чекбокс**: текст «Я согласен
   с политикой конфиденциальности персональных данных и даю своё согласие на их
   обработку» (слова «политикой конфиденциальности» — ссылка на `privacy.html`), кнопка
   заблокирована (`disabled`), пока чекбокс не отмечен. Механика через
   `state.consent` / `toggleConsent` / `consentOk` — скопируй один в один с уже готовой
   формы в другом городе (проще всего с `tyumen/corporate.html`), это часть общего
   компонента `DCLogic`, там же живёт и вызов Bitrix24 (см. секцию про Bitrix ниже).

8. **Фавикон.**
   Скопировать `favicon-32x32.png` и `apple-touch-icon.png` (и `favicon.png` про запас)
   из `tyumen/uploads/` в `<город>/uploads/`, и добавить в `<head>` каждой страницы:
   ```html
   <link rel="icon" type="image/png" sizes="32x32" href="uploads/favicon-32x32.png">
   <link rel="apple-touch-icon" sizes="180x180" href="uploads/apple-touch-icon.png">
   ```

9. **Добавить город на корневую страницу выбора** (`index.html` в корне репозитория) —
   карточка со ссылкой на `<город>/index.html`.

10. **Отревизировать оставшиеся конкретно для этого экспорта косяки** — см. следующий
    раздел, они повторяются от города к городу.

## Известные особенности экспорта (проверять в КАЖДОМ новом городе)

- **Не все страницы подвала приходят одинаково рабочими.** У Ижевска 13 из 17 страниц
  сразу пришли с рабочим подвалом (кто-то уже прошёлся раньше), а `index.html`,
  `afisha.html`, `bowling.html`, `kitchen.html` — с полностью пустым, все 28 ссылок были
  `href="#"`. Не полагайся на то, что подвал одинаков на всех страницах — прогоняй
  проверку по каждой странице города отдельно.
- **`<image-slot>` без картинки.** Это виджет дизайн-инструмента: он подтягивает фото из
  служебного файла `.image-slots.state.json`, которого в репозитории нет и не будет (это
  файл редактора, не часть деплоя). Поэтому на живом сайте все `<image-slot>` без
  явного `src=` показывают только текст-плейсхолдер вместо фото. Это не баг переноса —
  так было и остаётся во всех городах, пока кто-то не подставит реальные фото на замену
  этого механизма. Известные слоты: hero-фото «о нас», фото филиалов, постеры
  стендап-концертов в афише, промо-фото. (Слоты с `src=` — например картинки уровней
  карты гостя в `loyalty.html` — заполнены нормально, их не трогать.)
- **ID слотов и названия филиалов копируются от прошлого города.** У Ижевска
  `filial-matrix.html` и `filial-petrovsky.html` содержали `<image-slot id="filial-ostrov-hero">`
  и `id="filial-sitimoll-hero"` — то есть буквально id тюменских филиалов, скопированные
  вместе с версткой. Аналогично селект точки в формах бронирования (`<select>` в модалке)
  и в футере «ТОЧКИ СЕТИ» может прийти со списком филиалов прошлого города или с лишним
  задублированным пунктом (у Ижевска был `Петровский, Матрица, Петровский` вместо
  `Петровский, Матрица`, и в 8 формах, и в общем футере). Проверяй `id=` у всех
  `<image-slot>` и содержимое всех `<select>`/списков филиалов на соответствие
  реальным точкам нового города.
- **2GIS/Яндекс.Карты ссылки могут указывать не на тот город** (замечено на
  `izhevsk/index.html` — ссылка на 2GIS вела на `2gis.ru/tyumen/search/...` вместо
  `izhevsk`). Не исправлено — не забудь проверить при следующей правке.
- **Шапка: выпадашка «ВЫБЕРИТЕ ГОРОД» (`data-m="city-pick"`) часто приходит битой.**
  Обнаружено в Сургуте и повторилось в Самаре (обе явно копировались от предыдущего
  города со сломанной шапкой): ссылки на другие города в дропдауне — без `../` (то есть
  `href="izhevsk/index.html"` вместо `href="../izhevsk/index.html"`), и/или в списке не
  хватает какого-то города (у Сургута и Самары не было Тюмени). Эталон — Тюмень, Ижевск,
  Нижневартовск, там всё верно (все 7 городов, все ссылки с `../`, кроме self →
  `index.html`). Блок побайтово одинаков на всех страницах одного города (кроме
  `index.html`/`afisha.html`/`bowling.html`/`kitchen.html` — там этого дропдауна нет
  вообще, это нормально, так во всех городах). Проверяй в КАЖДОМ новом городе.
- **Виджеты локаций (карта на `_geoData()`/`VENUES`/`pts` в `index.html`, `afisha.html`,
  `bowling.html`, `kitchen.html`) могут прийти с координатами и списком точек от
  прошлого города.** В Самаре был классический кейс: массив `VENUES` (карточки филиалов)
  содержал 3 записи вместо 2 — `Гудок` было продублировано, а `lat/lng` у всех трёх
  указывали на реальные тюменские координаты (57.1×, 65.5×) вместо самарских (53.1×,
  50.0×/50.1×). То же самое было в `_geoData()` (сетевая карта всех городов): ключ
  `'Самара'` был задублирован дважды (второй объект в JS-литерале молча перезаписывает
  первый), Тюмень в списке городов отсутствовала, а «выигрывающая» версия самарской точки
  показывала один плейсхолдер-маркер «Адрес уточняется» вместо двух реальных филиалов.
  Отдельно — на `filial-*.html` встроенная Яндекс-карта (`<iframe src="...map-widget...">`)
  тоже может содержать координаты прошлого города в параметрах `ll=`/`pt=` (в Самаре оба
  `filial-gudok.html` и `filial-letout.html` показывали тюменскую точку на карте).
  Проверяй все координаты (`lat:`/`lng:`/`ll=`) на соответствие региону нового города.
- **Схема зала (`HALLSCHEME`/`_hs` в `afisha.html`) почти всегда указывает на тюменские
  PNG** (`uploads/hall-city.png`, `uploads/hall-ostrov.png`, `uploads/hall-columb.png` —
  это реальные планы тюменских залов СитиМолл/Остров/Колумб). Подтверждено в Самаре,
  Сургуте и Нижневартовске — ни для одного из них своих планов зала нет, эта часть не
  исправлена нигде. У Сургута и Нижневартовска (1 филиал) объект `_hs` вдобавок содержит
  один и тот же ключ трижды (`{'Аура': ..., 'Аура': ..., 'Аура': ...}`), из-за чего в JS
  побеждает последнее значение — `hall-columb.png`. Нужны реальные планы залов от
  заказчика на каждый город; до тех пор это известный, не закрытый пробел в контенте.
